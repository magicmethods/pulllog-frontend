# E2E テストアーキテクチャ

## 1. 目的
このドキュメントは、リポジトリ全体で利用する Playwright E2E テストのアーキテクチャを定義します。

目的は次のとおりです。
- 重要なエンドツーエンドの業務挙動を検証する
- E2E の対象範囲を意図的かつ限定的に保つ
- 再現可能なマニフェスト駆動の実行を支える
- PC・タブレット・スマートフォンを対象にした標準デフォルトのデバイスマトリクスを用いる
- 共通レポートテンプレートから、すべての実行で Markdown レポートを生成する
- 必要に応じて、成功した実行の証跡を PDF として保管する

## 2. E2E の対象範囲
E2E テストは、統合された複数の層をまたいで、ユーザーから観測可能な業務フローを検証するために存在します。

E2E に適した挙動の例:
- 認証を経て保護されたページへ到達すること
- 重要なユーザーワークフローを完了できること
- ユーザーに見える状態が保存され、再読込後も復元されること
- ルート保護やロールベースアクセス制御がユーザーレベルで正しく機能すること
- 主要ページが現実的な条件下で表示され、正常に動作すること

通常は E2E に含めないほうがよい挙動の例:
- 純粋なユーティリティ関数
- ローカルなフォーマット処理
- 狭い範囲のコンポーネント表示詳細
- 単体テストや結合テストで扱うほうが適切な複雑なエッジケースの組み合わせ

## 3. 原則
- マニフェスト駆動の実行
- 意図された 1 シナリオにつき 1 つの `case id`
- 対象に含める範囲と除外する範囲を明示する
- レポートおよび証跡パスは決定的であること
- 脆いセレクタよりも安定したロケータを優先する
- 任意の sleep よりも状態ベースの待機を優先する
- 生の認証情報ではなくアカウント参照を使う
- spec 間の重複を最小限にする

## 4. リポジトリ構成
推奨構成:

- `docs/architecture/e2e-test.md`
- `e2e/cases/` : ケースマニフェスト置き場
- `e2e/manifests/` : 任意のグループ実行マニフェストやインデックス
- `e2e/reports/` : Markdown 実行レポート
- `e2e/evidence/` : 保管用 PDF 証跡
- `e2e/templates/` : Markdown / PDF レイアウトテンプレート
- `e2e/templates/pulllog/` : リポジトリ提供の Pulllog 既定テンプレートセット
- `tests/e2e/core-flows.spec.ts` : 現在の中核となるマニフェスト駆動シナリオのエントリポイント
- `tests/e2e/pages/` と `tests/e2e/support/` : ページオブジェクトと共通ヘルパー
- `tests/playwright/` : Playwright 設定とレポーター統合

## 5. ケースマニフェストモデル
各 E2E ケースは JSON マニフェストとして定義します。

ケースマニフェストには次を記述します。
- case id
- 有効 / 無効状態
- 環境名
- `baseURL` または `baseURL` 参照
- アカウント参照キー
- 対象ページまたはルート
- ナビゲーション前提
- 対象に含める範囲と除外する範囲
- 前提状態
- レポート生成の挙動
- タグ
- 備考

マニフェストは `e2e/cases/case.schema.json` に対して検証されます。

## 6. 環境戦略
環境固有の値を spec 全体へ散在させてはいけません。

優先順:
1. リポジトリ設定または Playwright 設定
2. 環境変数または安全なシークレット
3. マニフェスト参照
4. 本当に安定かつ非機密な場合のみ直接リテラルを書く

各実行では、次を記録する必要があります。
- 環境名
- 解決後の `baseURL`
- case id
- 実行日時

### Runtime lane 方針
このリポジトリでは、frontend E2E 実行レーンを次の 2 つに定義します。
- `local-e2e` を標準既定レーン
- `local-dev` を例外レーン

運用ルール:
- 開発時・テスト時の既定は `local-e2e` とする
- frontend と backend は常に同じレーンで起動する
- レーン不一致の組み合わせはセットアップ失敗として扱う

### local-dev を許可する例外条件
`local-dev` は次のいずれかを満たす場合のみ許可します。
- Playwright 管理外で `https://pull.log:4649` の実ホスト挙動を検証する必要がある
- `local-e2e` で再現できない外部常駐プロセスやローカルデータに依存する
- 開発ホストに紐づく cookie / certificate / host 固有挙動を検証する

上記に該当しないケースは `local-e2e` で実行します。

## 7. アカウント戦略
ケースマニフェストに生の認証情報を保存してはいけません。

代わりに次を行います。
- `accountKey` を保存する
- 実際の認証情報は安全な設定または credential provider から解決する
- 必要に応じて、アカウントのロールや用途を生のテストファイル外で文書化する

想定されるアカウント分類:
- 匿名ユーザー
- 一般ユーザー
- 管理者ユーザー
- 読み取り専用ユーザー
- 期限切れまたはブロック済みユーザー
- シードデータ専用アカウント

## 8. カバレッジ境界の制御
あるケースでは、対象範囲から意図的に一部フローを除外してよいものとします。

典型的な除外対象:
- ログインフロー
- 対象ページへ到達するまでの完全なナビゲーション経路
- オンボーディングフロー
- 上流側のデータ作成フロー

この考え方が必要な理由:
- ケースによっては、ルート遷移そのものではなく特定ページ状態を対象にしているため
- 一部のカバレッジは別の専用ケースで扱うべきため
- 責務を分割することで flakiness を減らし、診断しやすくするため

除外内容はマニフェストに明示しなければなりません。

## 9. レポート方針
すべての E2E 実行で Markdown レポートを生成しなければなりません。

レポートには次を含める必要があります。
- 実行サマリー
- ケースメタデータ
- 前提条件
- 対象に含めるカバレッジ
- 対象から除外するカバレッジ
- 主要アサーション
- 結果
- アーティファクト参照
- 必要に応じて失敗サマリー

推奨レポートパス:
- `e2e/reports/YYYY-MM-DD/<case-id>/report.md`

同一ケースに対して複数の Playwright project を実行した場合、生成される `report.md` はすべての実行 project の結果を 1 つのケースレポートに集約し、project ごとの要約表を含み、各 project のアーティファクト情報や失敗情報も保持する必要があります。

### レポートテンプレート方針
レポート生成における正本テンプレートファイルは次のとおりです。
- `e2e/templates/report-template.md` : ケース単位の Markdown レポート
- `e2e/templates/index-template.md` : 日次サマリーのインデックス
- `e2e/templates/evidence-template.html` : 任意の PDF 証跡レイアウト

また、このリポジトリでは Pulllog 専用の既定テンプレートセットも提供します。
- `e2e/templates/pulllog/report-template.md`
- `e2e/templates/pulllog/index-template.md`
- `e2e/templates/pulllog/evidence-template.html`

これらのテンプレートファイルが存在する場合、レポート生成はレポーターコード内にレイアウトをハードコードするのではなく、実行時メタデータを差し込んで描画するべきです。

### テンプレート上書き戦略
上記の既定テンプレートは、リポジトリのベースラインとしてコミットされた状態を維持します。

上書きの優先レイヤーは次のとおりです。
1. `e2e/templates/` 内のリポジトリ既定テンプレート
2. `.env.e2e` からの任意のグローバル上書き
3. マニフェストの `report.templates` ブロックからの任意のケース別上書き

サポートされるグローバル環境変数:
- `PLAYWRIGHT_E2E_TEMPLATE_DIR` : `e2e/templates/` 配下のサブディレクトリでテンプレート一式をまとめて切り替える
- `PLAYWRIGHT_E2E_REPORT_TEMPLATE` : ケース単位 Markdown テンプレートのみを上書きする
- `PLAYWRIGHT_E2E_INDEX_TEMPLATE` : 日次サマリーテンプレートのみを上書きする
- `PLAYWRIGHT_E2E_EVIDENCE_TEMPLATE` : PDF 証跡 HTML テンプレートのみを上書きする

現在の Pulllog リポジトリ既定では、`.env.e2e` で `PLAYWRIGHT_E2E_TEMPLATE_DIR=pulllog` を設定し、ベースラインテンプレートを変更せずに日本語の Pulllog ブランドテンプレートを有効化できます。

ケース別マニフェスト上書きでは次を定義できます。
- `report.templates.markdown`
- `report.templates.evidence`

相対パスの上書き値はまず `e2e/templates/` を基準に解決し、必要に応じて明示的な相対パスまたは絶対パスもサポートします。
マニフェストファイル名も決定的であるべきで、通常は定義している `case id` と一致させます。

## 10. 証跡保管方針
実行が成功し、かつマニフェストで保管が許可されている場合は、Markdown レポートを PDF に変換して証跡として保存します。

推奨証跡パス:
- `e2e/evidence/YYYY-MM-DD/<case-id>/report.pdf`

失敗した実行では、Markdown と技術的アーティファクトは保持してよいですが、既定では最終 PDF 証跡を生成しません。

同一ケースに対して標準マトリクスの複数 project が存在する場合、PDF 証跡には詳細な project 別セクションに加え、固定の PC / タブレット / スマートフォン比較表を描画する必要があります。

## 11. アーティファクト方針
アーティファクトには次が含まれます。
- スクリーンショット
- トレースファイル
- 動画
- コンソールログ
- ネットワークサマリー

アーティファクトは追跡不能な状態で埋もれさせるのではなく、Markdown レポートから参照されるべきです。

## 12. 実行モード

### デフォルトの project マトリクス
ケースやコマンドで project 選択を明示的に上書きしない限り、標準 E2E 実行では次を対象にします。
- PC: `chromium`
- タブレット: `ipad-pro-11`
- スマートフォン: `iphone-14`

`firefox`、`webkit`、`android-pixel-7` などの追加 project は、互換性確認のために任意で利用できますが、アーキテクチャ上の既定ベースラインではありません。

サポートされる実行モードの例:
- 単一ケース実行
- タグ単位実行
- マニフェスト一覧によるバッチ実行
- CI 実行

CLI で対象 project を明示的に絞る場合は、独自のフィルタロジックを作るのではなく、`--project=chromium,ipad-pro-11,iphone-14` のようなカンマ区切り指定（または妥当な部分集合）でリポジトリの既存ランナーを使います。

バッチ実行では、spec コードにハードコードされた一覧ではなく、マニフェストファイルまたはグループ化されたマニフェストインデックスからケースを解決すべきです。

### レーン統一起動タスク
レーン不一致を防ぐため、ローカル E2E 実行時の起動/停止は VS Code タスク経由を必須とします。
- `Frontend E2E Lane: Start unified stack`
- `Frontend E2E Lane: Stop unified stack`
- `Frontend E2E Lane: Restart unified stack`

タスクの挙動:
- frontend `:43173` と backend `:3030` がすでに健全なら起動をスキップ
- どちらかが不整合なら対象ポートを解放して同一レーンで再起動
- 停止タスクで両プロセスをまとめて停止し、クリーンに再起動可能な状態へ戻す

E2E 実行時に片側だけ手動起動する運用は禁止します。

## 13. レビュー基準
健全な E2E ケースは、次のすべてを満たすべきです。
- E2E で扱うべき内容である
- 目的が明確である
- 前提条件が明示されている
- 対象に含める範囲と除外する範囲が明示されている
- 安定したロケータ戦略を使っている
- 有用なレポートを生成する
- アーティファクトから診断可能である
- 説明のない sleep や脆い順序依存を必要としない

## 14. 変更管理
E2E の挙動を追加または変更する場合:
1. ケースマニフェストを更新または作成する
2. spec を更新または追加する
3. 関連するケースを実行する
4. Markdown レポートを生成する
5. 成功し、かつ許可されていれば証跡を保管する
6. 安定性と対象範囲をレビューする

## 15. Agent 駆動ワークフロー
このリポジトリでは、E2E 作業の入口として `frontend-orch-e2e` を使います。

- `frontend-orch-e2e` : ステージ振り分けと全体進行
- `frontend-design-e2e-scenario` : シナリオとマニフェストの設計
- `frontend-impl-e2e-playwright` : spec 実装と検証
- `frontend-debug-e2e` : 失敗再現と最小修正
- `frontend-review-e2e` : 保守性と証跡品質のレビュー

推奨される実作業フロー:
1. Copilot Chat を開き、`frontend-orch-e2e` または prompt の `Start Frontend E2E Workflow` から開始する
2. `frontend-orch-e2e` に、ケース範囲整理と `frontend-design-e2e-scenario` への振り分けを依頼する
3. 提案された `case id`、タグ、対象に含める範囲、除外する範囲、前提条件をレビューして承認する
4. `frontend-orch-e2e` から `frontend-impl-e2e-playwright` へ実装を進める
5. まず最小限の対象範囲でケースを検証する。通常は次:
   - `pnpm run test:e2e:case -- <case-id> --project=chromium`
6. その後、必要に応じて標準マトリクスでも検証する:
   - `pnpm run test:e2e:case -- <case-id> --project=chromium,ipad-pro-11,iphone-14`
7. 実行が失敗した場合は、レポートパス・アーティファクト・失敗範囲を添えて `frontend-debug-e2e` へ切り替える
8. 実行が安定したら、`frontend-review-e2e` にマニフェスト / spec / レポート / 証跡品質のレビューを依頼する
9. ケースが成功し、保管が許可されていれば、生成済み Markdown レポートから PDF 証跡を出力する
10. 一時的な Playwright アーティファクトではなく、意図したソース / ドキュメント変更のみをコミットする

### 推奨プロンプトテンプレート
次のようなプロンプトを使います。

`frontend-orch-e2e` 向け:
> `<target behavior>` の E2E 作業をオーケストレーションしてください。シナリオ設計、実装、失敗調査、レビューのどこから始めるべきか判断し、既定マトリクス（`chromium`, `ipad-pro-11`, `iphone-14`）を前提に必要ステージを整理してください。

`frontend-design-e2e-scenario` 向け:
> `<target behavior>` のためのマニフェスト駆動 E2E ケースを設計してください。既定マトリクス（`chromium`, `ipad-pro-11`, `iphone-14`）を維持し、対象に含める範囲・除外する範囲・前提条件・タグを定義し、`e2e/cases/<case-id>.json` を提案してください。

`frontend-impl-e2e-playwright` 向け:
> 承認済みの `<case-id>` を、現在のマニフェスト駆動構成（`e2e/cases/`, `tests/e2e/core-flows.spec.ts`, page objects, support helpers）に従って実装してください。可能な限り既存ヘルパーを再利用し、まず `pnpm run test:e2e:case -- <case-id> --project=chromium` で検証してください。

`frontend-debug-e2e` 向け:
> 最新の `e2e/reports/.../report.md` と Playwright アーティファクトを使って、`<project>` 上での `<case-id>` 失敗を再現してください。根本原因を分類し、正当化できる最小修正を適用したうえで、関連範囲を再実行してください。

`frontend-review-e2e` 向け:
> `<case-id>` について、対象範囲、安定性、マニフェスト整合性、Markdown / PDF レポート品質、長期保守性をレビューしてください。`Must fix`、`Should fix`、`Nice to have`、`Final verdict` を返してください。

### コミット範囲の指針
ワークフローが完了した際、通常のコミットに含めてよいもの:
- `docs/architecture/e2e-test.md`
- `.github/agents/` と `.github/skills/` の変更
- `e2e/cases/*.json`
- `tests/e2e/` と `tests/playwright/` のソース変更
- 関連する README またはアーキテクチャメモ

`tests/test-results/` などの一時生成物は、明示的な理由がない限り含めてはいけません。

## 16. オープンな設計メモ
このドキュメントは、E2E プロセスに関する意思決定のためのアーキテクチャ上の正本です。
実装詳細は進化してもよいですが、責務分離は維持されるべきです。

- アーキテクチャはここに記述する
- ケースごとの挙動はマニフェストに記述する
- 実装は spec と fixture に置く
- 実行とレポート生成は skill に持たせる
- 役割別の推論は agent に持たせる
